## 一、项目整体结构

### 1.1 三个子项目

| 子项目 | 定位 | 技术栈 | 端口 | 启动入口 |
|---|---|---|---|---|
| `class1/02api-proxy` | A1 统一模型服务：对外 OpenAI 协议，对内适配混元/DeepSeek/智谱/Kimi | Node.js 原生 HTTP（无框架）+ `ai` SDK 4.x | **11434** | `npm start` |
| `class2/web_ui` | A2 客服工作台：对话 UI、多会话、流式打字机、引用来源渲染 | Vite 5 + React 18 + TypeScript + Zustand | **3098** | `npm run dev` |
| `class3` | A3 知识增强：LangGraph 自适应 RAG | Python + LangGraph + FastAPI + Chroma | **14052** | `.venv\Scripts\python.exe server.py` |

### 1.2 依赖关系

```
浏览器 ──► class2 (:3098) ──┬─ direct ──► /tokenhub（Vite 代理）──► TokenHub 中国站
                            ├─ proxy  ──► class1 (:11434) ───────► TokenHub 中国站
                            └─ rag    ──► class3 (:14052) ───────► TokenHub 中国站
                                          └─ Chroma（本地向量库 db_md）

依赖方向：class2 → class1（可选）、class2 → class3（可选）；class1 与 class3 当前互不依赖。
同一会话只能处于三种模式之一（单选切换），三者可同机并存、端口无冲突、CORS 互开。
```

**class3（约 950 行）**：
| 模块 | 职责 |
|---|---|
| `server.py` | FastAPI：`/health`、`/`、`POST /chat`（多轮 session）、`POST /chat/reset` |

## 五、发现的问题

| # | 级别 | 问题 | 现象与根因 | 建议 |
|---|---|---|---|---|
| 1 | **中（新发现）** | hy3 为思考型模型，`max_tokens` 给小会导致 **content 为空** | 实测 `max_tokens=200` 时 200 tokens 全被 `reasoning_content` 消耗，`content=""`、`finish=stop`；调到 1500 仍可能被思考耗尽 | 前端默认 4096 已可覆盖；调用方勿把 `max_tokens` 设过小；判断成功应同时看 `reasoning_content`，不能只看 `content` |
| 2 | 中（已知） | RAG 单问耗时 54~93s | 一次提问触发 4~8 次串行模型调用（路由/改写/逐文档评分/生成/双评分），非流式为设计使然 | 演示前先"预热"一次；UI 侧已有加载态，勿误判为卡死 |
| 3 | 低（已复核仍存在） | 纯空白问题触发 4 轮检索循环 | 输入 `"   "` 可通过 `min_length=1` 校验，进入检索环直至熔断：134s，steps 出现 4 组 `transform_query→retrieve→grade_documents`，最终回复"资料不足，建议转人工" | 服务端对 `question.strip()` 为空直接返回 400 |
| 4 | 低（已复核仍存在） | `npm run lint` 不可用 | `eslint` 依赖已装但缺配置文件，提示 "ESLint looked for configuration files..." | 补 `.eslintrc.cjs` 或移除 lint 脚本 |
| 5 | 低（已复核仍存在） | 流式结尾重复 `finish_reason:"stop"` 帧 | 实测 `finish_frames=2 ['stop','stop']`，上游帧透传后又补发一条 | 记录已发送标记，收尾时跳过 |
| 6 | 低（本次已修） | 文档路径过时 | README 写 `E:\csk_project`，实际在 `F:\csk_project` | 已修正三处启动路径并加注迁移说明 |
| 7 | 提示（安全） | 两处 `.env` 明文持有可用 Key | TokenHub Key 已在教学环境多次使用 | 交付/截图前打码；建议轮换 Key |
| 8 | 提示（环境） | class3 的 chromadb 依赖 venv 内 MSVC 运行库补丁 | 系统 MSVC 运行库较旧会触发 `0xC0000005`；修复 DLL 已放在 `.venv` 内 | **重建 venv 后必须重做**，或安装官方 VC++ 2015-2022 运行库永久解决 |

## 六、注意事项（运维与演示）

1. **启动顺序建议**：class3 → class1 → class2。虽无硬依赖，但先起后端可避免设置面板出现"连接失败"字样。
2. **默认模式是"直连 API"且未填 Key**，首次打开需在右上角设置里切到「实训二代理」或「实训四 RAG」，或在直连模式填入 Key。本次 UI 测试即通过写入 localStorage 切模式完成。
3. **端口冲突**：11434 是 Ollama 默认端口；本机若启动 Ollama 需改 class1 的 `PORT` 并同步前端 `proxyUrl`。
4. **会话与熔断计数都在进程内存**：class3 重启即清空历史；前端持有旧 `session_id` 时会自愈（已实测），但上下文会丢。
5. **向量库维护**：改 `class3/data/md` 或换 Embedding 模型后，需 `REBUILD_VECTORSTORE=True` 重启一次建库，完成后改回 `False`；建库崩溃过则先删 `db_md` 再重建。
6. **地域一致性**：三端基址必须都是中国站 `https://tokenhub.tencentmaas.com/v1`，否则 401/401002。
7. **无鉴权、CORS 全开**：仅限本机或受信内网；跨机演示需把前端 `localhost/127.0.0.1` 换成服务机 IP。
8. **并发注意**：class3 的熔断计数器是类级共享变量，多人同时提问会互相干扰（单人演示无碍）。
